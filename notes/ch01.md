# Ch01 - Compiling

## In my own words

Rust is so fast because we separate compile time from runtime, which means we do a whole lot of checks and (possibly) optimisation during compile, which leaves only a fast executable for runtime.
`otool -L <executable>` shows the dynamic libraries the executable/binary needs at runtime.
In our case, `hello` is multiple hundreds of kb because Rust statically links its standard library, which is copied into the binary. `otool` shows only `libSystem`, the library needed to talk to Mac hardware, because nothing else is needed.

## What surprised me

For the race, I predicted 5s for Python, 2s for sum_debug and <1s for sum_release. So I was spot on for the first one, above for the 2nd, and the final one took me by surprise. It's amazing to me that the compiler optimised the code by replacing the loop with its result, so only a constant print remains at runtime.

## What is still fuzzy

I must admit I'm not entirely in the clear on what exactly happens with undefined symbols during compile time and linking.
After compilation, `hello.o` has 5 U symbols. `std::io::stdio::_print` and `<&T as core::fmt::Display>::fmt` are both used by `println!("Hello, {name}!")`. `_print`is obvious, and `Display::fmt` is the standard library method for showing the value of `name` as human-readable text. Its Python counterpart would be `__str__`. `_rust_eh_personality` is exception handling, and this works similarly: the compiler shows these as undefined, but the linker brings them into the binary.
`std::rt::lang_start_internal` is there because the compiler generates a C-style `_main`. It calls `lang_start_internal` which sets up the runtime before calling the Rust `main` function.
Lastly, `__Unwind_Resume` is dynamically linked because it comes from the OS. `libSystem` is the interface to the OS, so it can't be brought into the binary. This is why it shows in the `otool` call described above.
